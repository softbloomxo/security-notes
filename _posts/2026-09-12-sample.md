> これは、許可を得た検証環境での調査を想定したWriteupの記入例です。対象に合わせてIPアドレス、結果、判断理由を書き換えてください。

## 1. Target Information（対象情報）

| 項目 | 内容 |
|---|---|
| Target | `192.168.56.101` |
| OS | Linux（検証環境） |
| Goal | `user.txt` と `root.txt` の取得 |

対象マシンをホストオンリーの検証ネットワークに配置し、攻撃用マシンから疎通を確認した。

```bash
ping -c 1 192.168.56.101
```

## 2. Reconnaissance（事前調査）

まず、公開されているポートとサービスを確認した。

```bash
nmap -Pn -sC -sV -oN scans/initial.txt 192.168.56.101
```

結果から、HTTPサービスが公開されていることを確認した。以降はWebアプリケーションの構成と、公開されているディレクトリを中心に調査する。

## 3. Enumeration（列挙）

ブラウザでトップページを確認した後、よく使われるディレクトリ名を対象に列挙を実施した。

```bash
gobuster dir -u http://192.168.56.101/ \
  -w /usr/share/wordlists/dirb/common.txt \
  -x php,txt,bak
```

`/admin/` と `/backup/` が見つかった。`/admin/` は認証画面だったため、URL、画面の挙動、レスポンスヘッダを記録した。`/backup/` には古い設定ファイルが残っていないかを慎重に確認した。

## 4. Vulnerability Identification（脆弱性の特定）

`/backup/` 配下のファイルには、開発用に残された設定情報が含まれていた。本文に認証情報やトークンをそのまま記載する場合は、公開前に必ず伏せ字にする。

今回のポイントは「不要になったバックアップファイルがWebから参照できる状態だった」ことだった。発見した情報をもとに、アプリケーションの管理機能で使われているアカウントを特定した。

## 5. Exploitation（攻撃・侵入）

検証環境内で、特定したアカウントを使って管理画面へログインできることを確認した。ログイン後は、アプリケーションがファイルを扱う機能の権限を確認し、想定外の場所へアクセスできないかを調べた。

この段階では、次の3点を記録しておくとWriteupが読みやすくなる。

- 入口になった機能と、その画面URL
- 何を確認して脆弱性と判断したか
- 侵入後に取得できた権限と、できなかった操作

検証用フラグを確認できたため、`user.txt` を取得した。

```text
flag{sample_user_flag}
```

## 6. Privilege Escalation（権限昇格）

侵入後は、現在のユーザー権限と実行できる管理コマンドを確認した。

```bash
id
sudo -l
find / -perm -4000 -type f 2>/dev/null
```

調査の結果、管理者権限で実行できる設定スクリプトが見つかった。スクリプトの入力値と実行パスを確認したところ、一般ユーザーが変更できるファイルを参照していたため、検証環境で権限昇格を再現できた。

最後に、root権限でフラグを取得した。

```text
flag{sample_root_flag}
```

## 7. Conclusion（まとめ）

今回の入口は、公開されたバックアップファイルと管理画面の設定だった。調査では、ポート確認だけで終わらせず、ディレクトリ列挙、設定ファイル、権限設定の順に確認することが有効だった。

公開用Writeupでは、再現に必要なコマンド、判断の理由、取得できた情報を時系列で残すと、後から読み返しやすくなる。
